## 3. Модель

**Базовий клас `Booking`** (`src/kzp_lab06/models.py`) має `__slots__ = ("_room", "_guest", "_check_in", "_check_out", "_rate")`, тож об'єкт не може отримати випадкове нове поле через одруківку.

| Властивість | Доступ | Інваріант (setter) |
| :-- | :-- | :-- |
| `room` | читання/запис | `int` (не `bool`), більше нуля |
| `guest` | читання/запис | `str`, після нормалізації пробілів не порожнє |
| `rate` | читання/запис | число (не `bool`), скінченне, не від'ємне; нуль дозволено |
| `check_in`, `check_out` | лише читання | `date`; `check_out` пізніше за `check_in` (перевіряється в `__init__`) |
| `nights`, `cost` | лише читання | `(check_out − check_in).days`, `nights × rate` |
| `tier` | лише читання | назва рівня підтипу |
| `sort_key` | лише читання | `(room, check_in, guest)` — ключ впорядкування |

`__init__` присвоює `self.room`, `self.guest`, `self.rate` через властивості, тому конструктор і пізніша зміна поля перевіряються одним кодом. Setter записує у внутрішнє поле `self._rate`, а не в `self.rate`, інакше він викликав би сам себе.

Спеціальні методи:

* `__str__` — текст для звіту: `101 | Doe, John | 2026-01-01..2026-01-04`;
* `__repr__` — клас і всі поля: `StandardBooking(room=101, guest='Doe, John', ...)`;
* `__eq__` — `NotImplemented` для об'єкта іншого типу; рівні лише об'єкти одного класу з однаковими полями (Standard і Premium з тими самими полями не рівні);
* `__hash__ = None` — змінюваний об'єкт не можна покласти в множину чи використати ключем словника;
* впорядкування — через `key=lambda b: b.sort_key`, а не `__lt__`.

Повідомлення setter-ів збігаються з повідомленнями ЛР № 6, тому `loader` лише додає номер рядка: `Рядок 3: поле rate має бути числом`.

## 4. Dataclass

```python
@dataclass(frozen=True)
class Occupancy:
    occupied: int
    total: int
    # property percent -> occupied / total * 100 (0.0 для порожнього входу)


@dataclass(frozen=True)
class ReportSummary:
    reference_date: date
    count: int
    active: tuple[Booking, ...]
    occupancy: Occupancy
    count_by_rate: tuple[tuple[float, int], ...]
    guests: tuple[str, ...]
    longest_stay: Booking | None
    total_nights: int
    total_cost: float
```

`@dataclass` автоматично створює `__init__`, `__repr__` і `__eq__` за полями. `frozen=True` забороняє зміну поля після створення (`FrozenInstanceError`), тому підсумок є простим незмінним значенням: його будує `analysis.build_report`, а `reporting.format_report` лише читає. Колекції всередині збережено кортежами, щоб і вони не змінювалися. `Occupancy` — це підсумок варіанта «завантаження номерів»; він хешується й порівнюється за значенням.

## 5. Підтипи та протокол

Спільна операція — `total_price()`, ціна з надбавкою, округлена до копійки (`Decimal`, `ROUND_HALF_UP`):

| Підтип | Формула | Приклад (3 ночі × 1000.00) |
| :-- | :-- | :-- |
| `StandardBooking` | `cost × 1.05` | 3150.00 |
| `PremiumBooking` | `cost × 1.15 + 50.00 × nights` | 3600.00 |

У базовому класі `total_price()` викидає `NotImplementedError`. CSV не має колонки категорії, тому підтип обирає фабрика `create_booking`: тариф від `PREMIUM_RATE = 1000.00` включно → `PremiumBooking`, нижче → `StandardBooking`. Це єдине місце, де вибирається клас.

Протокол:

```python
class Priced(Protocol):
    @property
    def nights(self) -> int: ...
    @property
    def tier(self) -> str: ...
    def total_price(self) -> float: ...
```

Функції `analysis.total_revenue`, `revenue_by_tier` і `most_expensive` приймають `Iterable[Priced]` і викликають лише `item.total_price()` та `item.tier`. У модулі `analysis` немає `isinstance` і назв підтипів (це перевіряє тест). Duck typing підтверджено тестом зі стороннім класом `GiftCertificate`, який не наслідує `Booking`, але має потрібні атрибути.

Результат на `data/input.csv` (`--details`):

| :-- | :-- | --: | --: |

| 205 | Standard | 1543.50 | 1620.68 |
| 210 | Standard | 2000.00 | 2100.00 |

## 6. Модулі

| Модуль | Призначення |
| :-- | :-- |
| `models.py` | `Booking`, `StandardBooking`, `PremiumBooking`, `create_booking`, `Priced`, `Occupancy`, `ReportSummary`; не читає файлів |
| `loader.py` | `csv.DictReader` з UTF-8, перетворення тексту на `int`/`date`/`float`, створення об'єкта через `create_booking`; `TypeError`/`ValueError` моделі обгортаються в `DataError` з номером рядка (`raise ... from error`) |
| `analysis.py` | відбір активних, кількість за тарифом, гості, завантаження, найдовше проживання, `build_report`, потокова `stream_summary`, функції протоколу `Priced` |
| `reporting.py` | `format_report(summary)` — детермінований текст; `ReportWriter` і `write_report` — запис через `with`, `Path`, UTF-8, LF |
| `errors.py` | `DataError` |
| `cli.py` | `argparse`: вхідний і вихідний файл, `--reference-date`, `--details`; коди 0 / 2 / 3; запускається лише через `main()` |

**Контекстний менеджер `ReportWriter`** (завдання із зірочкою): `__enter__` створює каталог і відкриває тимчасовий файл `.<ім'я>.tmp` у тому ж каталозі; `__exit__` закриває файл і за успіху атомарно замінює звіт (`os.replace`), а за винятку видаляє тимчасовий файл і повертає `False`, тому виняток не маскується. Старий звіт у разі збою залишається цілим.

## 12. Відповіді на контрольні питання

1. **Чим клас відрізняється від екземпляра?** Клас — це опис: які поля та методи матиме об'єкт. Екземпляр — конкретний об'єкт цього класу з власними значеннями, наприклад одне бронювання номера 101.
2. **Яку роль виконує `__init__` і що означає `self`?** `__init__` заповнює щойно створений об'єкт початковими значеннями. `self` — посилання на цей конкретний об'єкт, через нього метод звертається до його полів.
3. **Для чого застосовується `@property`?** Щоб звертатися до значення як до поля (`booking.rate`), але за цим стояв метод: з перевіркою при записі або з обчисленням при читанні (`nights`, `cost`).
4. **Чому setter записує у внутрішнє поле, а не у властивість?** Присвоєння `self.rate = ...` всередині setter-а знову викликало б той самий setter — нескінченна рекурсія. Тому значення зберігається в `self._rate`.
5. **Яку поведінку автоматично додає `@dataclass`?** Генерує `__init__` за переліченими полями, `__repr__` з назвами полів і `__eq__`, що порівнює поля; за параметрами — ще впорядкування, хеш і незмінність.
6. **Навіщо застосовується `frozen=True`?** Об'єкт не можна змінити після створення, тож підсумок звіту не зміниться випадково; також такий об'єкт можна хешувати.
7. **Чим відрізняються `__str__` і `__repr__`?** `__str__` — зручний текст для користувача (рядок звіту), `__repr__` — точний технічний опис для розробника з класом і всіма полями.
8. **Як `__eq__` має поводитися з несумісним типом?** Повертати `NotImplemented`, а не `False` і не виняток. Тоді Python спробує порівняння з іншого боку, а якщо й воно не вдасться — результат `False`.
9. **Коли сортування через `key` краще за реалізацію `__lt__`?** Коли потрібен один або кілька різних порядків для конкретного звіту. `key` явно показує, за чим сортуємо, і не нав'язує класу «природний» порядок, якого в бронювань немає.
10. **Яку роль виконує `super()`?** Дає доступ до реалізації методу в батьківському класі (за MRO), щоб підклас міг розширити її, а не копіювати, наприклад викликати `super().__init__(...)` і додати власне поле.
11. **Що таке MRO і чому його потрібно враховувати?** Method Resolution Order — порядок класів, у якому Python шукає атрибут (`Class.__mro__`). Він важливий при множинному наслідуванні: від нього залежить, яку реалізацію викличе `super()`.
12. **Що означає качина типізація?** Важить не клас об'єкта, а наявність потрібних методів: якщо в об'єкта є `total_price()` і `tier`, функція доходу з ним працює.
13. **Яку проблему розв'язує `Protocol`?** Він явно записує контракт качиної типізації (які властивості й методи потрібні), щоб редактор і перевірка типів бачили помилку, не вимагаючи наслідування від спільного класу.
14. **Чому `analysis` не повинен перевіряти кожен конкретний підтип?** Інакше кожен новий підтип вимагав би правок у всіх функціях аналізу. Поліморфізм залишає формулу в самому підтипі, а аналіз лише викликає спільний метод.
15. **Де має виконуватися перетворення словника на об'єкт?** У `loader`, на межі між файлом і програмою: далі весь код працює вже з перевіреними об'єктами.
16. **Чому модулі не повинні запускати CLI під час імпорту?** Імпорт у тестах чи іншому модулі не повинен читати аргументи, файли чи завершувати процес. Тому запуск — лише в `main()` під `if __name__ == "__main__"` або через команду пакета.
17. **Які властивості об'єктів перевіряються тестами?** Що setter приймає коректні й граничні значення та відхиляє помилкові без зміни стану, що поля лише для читання не змінюються, похідні значення, `__str__`/`__repr__`, рівність і нерівність, незмінність dataclass, різні формули підтипів.
18. **Для чого потрібні pytest, ruff і wheel?** pytest перевіряє поведінку, ruff — помилки й стиль коду, wheel — що пакет збирається й працює після встановлення в чисте середовище.
19. **Які крайові випадки має містити тестовий набір?** Порожній вхід, нульове й граничне значення setter-а, межу вибору підтипу (999.99 / 1000.00), дубльований запис для рівності, пошкоджений рядок CSV, однакові дані в різних підтипах, виняток під час запису файла.
20. **Які результати потрібно задекларувати в REPORT?** Старий словниковий і новий об'єктний результати, класи й підтипи з формулами, повний звіт і доказ його сумісності, результати pytest, ruff, wheel і CLI, посилання на CI, артефакт і тег, Issues і PR, використання ШІ.

## 13. Висновки

Словникові записи ЛР № 6 замінено на об'єкти: базовий клас `Booking` перевіряє поля у setter-ах властивостей, підтипи `StandardBooking` і `PremiumBooking` по-різному рахують `total_price()`, а підсумок звіту став незмінним `@dataclass(frozen=True)`. Аналіз працює через протокол `Priced` без перевірки конкретного класу, тому новий рівень бронювання додається одним класом і рядком у фабриці. Формат CSV, текст звіту, повідомлення помилок і коди завершення не змінилися, що підтверджено автоматичним порівнянням зі збереженою словниковою моделлю. Об'єкти з `__slots__` займають приблизно вдвічі менше пам'яті, ніж словники. Окремі класи моделі, контекстний менеджер `ReportWriter` і 121 тест стануть основою для наступної роботи — власного зберігання об'єктів і інших Python-ідіом.
